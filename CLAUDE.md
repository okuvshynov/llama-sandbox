# CLAUDE.md

## Mistakes

These are the mistakes which were encountered in the past while working on this project. You MUST try hard to avoid these mistakes in the future.

- **Documentation drift during /commit**: When using `/commit`, README.md and TECHNICAL.md were not checked for staleness. Over multiple commits (file format changes, new subcommands, BF16 reference migration, prompt restructuring), the docs fell far behind — referencing old file formats (v3 trace files instead of stats files), old subcommand interfaces (`compare -a -b` instead of `compare -f`), stale prompt counts (12 instead of 19), and Q8 as reference when BF16 was adopted. Fix: during `/commit`, always check if key documentation files (README.md, TECHNICAL.md) reference concepts that were changed in the committed code. If the commit changes file formats, CLI interfaces, model configurations, or experiment methodology, update the docs in the same commit.

- **Piping long-running commands through `tail -N`**: Smoke / sweep commands like `python validation_bench_openai.py ... 2>&1 | tail -20` were used to keep the displayed output short. The downside: while the run is active you can't see streaming progress (turn-by-turn lines); and if something interesting happened in the discarded prefix, you have to rerun the whole thing to recover it. Fix: capture full output by redirecting to a file (or use `run_in_background: true` and read the output file the harness already creates), then `head`, `tail`, or `grep` against the saved file as needed. This preserves both progress visibility and the full transcript for later inspection.

- **Scoring-contract bugs ship without scorer unit tests**: Two scoring loopholes in validation-bench's contract evolution (vb_version 0.0.7 → 0.0.8 → 0.0.9) were missed in review and only surfaced via manual reproduction during ad-hoc validation. The 0.0.7 exit-code rule credited any timeout on an invalid input as a correct rejection (`rc != 0 → TN`); the 0.0.8 verdict-only rule credited "print right verdict, then crash" as a success. In both cases the "obvious" mental model held, but the rule's full input cross-product had untested holes. Fix: any change to `run_tests` scoring or `_fail_detail` formatting needs a test that exercises (right/wrong verdict) × (clean/dirty exit) × (timeout/crash/signal/no-output). The `_FakeSandbox` stub in `test_validation_bench.py` (no docker, no live model) makes adding scorer tests cheap — the bar to extending coverage when the contract changes should be near zero.

- **Alpine-based env Dockerfiles must `apk add coreutils`**: busybox's `timeout` (the alpine default) leaks one zombie process per invocation under the harness's `sh -c "timeout -s KILL Ns ./solution"` wrapper. The zombie is reparented to PID 1 (`sleep infinity`), which doesn't reap. With `--pids-limit=256`, a 678-test corpus saturates the cgroup at test ~#250; every subsequent test fails with `timeout: vfork: Resource temporarily unavailable`, which the harness records as `no output (exit=1)`. Symptom in the data: confusion matrices clustered like `TP=0, FN=205, FP=220, TN=253` — perfectly tracking the alphabetical test order in `tests.jsonl` (invalid first, valid second), with the cgroup saturating between the two halves. *Not* a model failure, *not* a parser bug — purely the combination of alpine + `--pids-limit=256` + 678 tests + busybox timeout. Verified opus's toml-1.0-zig validator scores MCC=+1.0000 once GNU coreutils' `timeout` (`apk add coreutils`) replaces busybox's. Same fix applies to any future alpine-based env (currently `data/envs/zig/`, `data/envs/go/`). Debian-based envs (cpp17, lua, erlang) ship GNU coreutils by default and are unaffected. The `validation_bench_lib.py:569` "Go runtime maps goroutines to OS threads" hypothesis was misdiagnosing this same root cause for Go.
- **llama.cpp op offload to the AMD-Metal GPU silently NaNs logits at batch ≥ 32 (Intel Mac Pro)**: On this Mac Pro 7,1 (AMD Radeon Pro Vega II Duo via Metal), llama.cpp's default `op_offload` ships large-batch host ops to the GPU once a decode batch reaches 32 tokens — even with `-ngl 0` and all weights on CPU. For GLM-5.2 Q6_K this produced NaN logits for *every* position of the batch; there is no error, no warning, and small batches on the identical setup are clean, so smoke tests pass and the corruption only appears when a longer sequence is decoded in one chunk (logit-kld's rescore at `-b 512` caught it; collect's 14-token prompt + 1-token generation steps never crossed the threshold). Diagnosis that separated the suspects: batch 16 chunks → clean (threshold confirmed); rebuild with `GGML_METAL=OFF`, batch 512 → clean (Metal offload guilty, Accelerate BLAS innocent). Fix adopted in logit-kld: force `GGML_METAL OFF` in the subproject's CMakeLists so the tools are CPU-only by construction. Watch-out for any other llama.cpp-based tool or server run on this machine: results computed with default build settings and batches ≥ 32 tokens are suspect; check for NaN/garbage logits before trusting them.

- **ggml logits are only bit-reproducible within one toolchain AND one thread count**: "bit-identical" is never a property of a model + token ids alone — it is a property of a *run configuration*, and two knobs beyond the known batch-shape one silently change the numbers. (a) **Thread count**: ggml partitions matmul work by `n_threads`, so the summation structure changes with `-t`. Measured on GLM-5.2 UD-Q6_K: `-t 16` vs `-t 32` produce different logits, while two runs at a fixed count are bit-identical even across cold/warm page cache. (b) **Compiler**: llama.cpp disagrees with *itself* by 8.85e-3 mean KL / 96.67% top-1 between an Apple-clang macOS build and an MSVC Windows build — same Xeon W-3245, same AVX-512 level, same llama.cpp commit, same CPU_REPACK fallback, same token ids. Cause is FP contraction in the plain-C kernels (Apple clang contracts `a*b+c` into FMA by default; MSVC at `/fp:precise` does not), not ISA. Both effects land at the *same order* as the batch-shape noise floor (~1e-2) and as the Q6_K_XL→Q6_K quant gap (6.7e-3) this tooling exists to measure, so either one can be mistaken for a real model difference or for a port bug. Consequences: every tool in a verification toolchain must share one thread-count default or an A/A between two of them measures thread noise (hence `logit-kld/src/cpu_topology.h`, shared by collect/rescore/nano-glm); each platform needs its OWN reference files; and baselines collected before 2026-08-06 used `hardware_concurrency()` = 32 logical, so comparing against them on this machine needs an explicit `-t 32`. When a KL==0 gate fails, check the run configuration before suspecting the code.

- **Verify the model bytes before debugging the code — and know that a hash right after a copy may only be checking the page cache**: a bit-exact gate that had passed for two days started failing by ~8.6e-04 mean KL (no token changes, below every documented noise floor, but enough to break byte-comparison). An hour went into eliminating source changes, ggml version, compiler flags, thread count, OpenMP team size and llamafile sgemm tiling — all identical, all innocent. The cause was two of fourteen GGUF shards being corrupt on disk. `sha256` against a known-good copy on the other machine found it in twenty minutes; **hashing the inputs should have been the first move, not the last.** Specifics worth keeping: (a) the corruption was ~1.9 KB spliced into two 40-50 GB files, which still had the correct size, parsed as valid GGUF, loaded without complaint and produced fluent text — nothing about it looked like corruption; (b) **the page cache masked it for a full day** — the copy wrote through cache, so runs that day read the still-correct cached pages and only a reboot exposed the bad bytes on disk, which also means a `Get-FileHash` immediately after a large copy verifies the cache, not the platter (verify again after a reboot, or bypass the cache); (c) **MoE routing made the damage position-dependent** — corrupt expert weights only perturb tokens that route to them, so some positions stayed bit-exact while others drifted, a pattern that looks nothing like a compiler or threading difference and which is a strong tell for bad weights; (d) the corrupt bytes were a *structured* in-memory descriptor table (repeating 8-byte records, 2 MiB stride, mostly not sector-aligned), i.e. a Windows writeback-DMA bug handing down the wrong source address — not bit rot, and invisible to ECC, WHEA, the storage error log and `chkdsk`, all of which stayed clean because nothing actually failed. Manifests and the diagnostic tools (`chunk_hash.py`, `bindiff.py`) live in `checksums/`; the damage shape is what distinguishes a driver bug from a hardware one, so diff a corrupt file against a good copy *before* overwriting it. Also: `Get-Volume` reports `HealthStatus: Warning` / `OperationalStatus: Full Repair Needed` and `FileSystemType: Unknown` for healthy exFAT volumes — it survives a clean `chkdsk`, so do not read anything into it.

- **On Windows, mmap-backed weights make timings unreproducible at half-TB scale**: benchmarking GLM-5.2 (582.87 GiB) with stock `llama-bench` on the Mac Pro under Windows returned tg32 = 1.84 ± 0.02 t/s in one invocation and 1.04 ± 0.29 in the next — same binary, same model, same thread count, differing only in standby-list state. `--load-mode none` (weights read into ordinary allocated memory) gives a steady 1.90 ± 0.08. macOS on the identical machine shows no such spread (± 0.00-0.01 across 5 reps). Consequences: never trust a single mmap-backed timing on Windows — re-run it, or use `-lm none`; and when a run's throughput looks anomalous, suspect paging before compute. This also explains why harness-style runs (collect/rescore/nano-glm, which page the model in *during* the measured window) read ~1.3 t/s against `llama-bench`'s ~1.84 warmed. Related trap: quoting a 2-rep benchmark at all — a 2-rep prefill sample suggested a 2x SMT gain that 5 reps flatly contradicted. Use `-r 5` and pp128+ on this model; short prefills (pp64) are dominated by paging noise (±27%).

- **`logit-kld/inspect.py` shadows a stdlib module — never put that directory on `sys.path`**: it is the reference reader for the lkldtopk format, so a new tool naturally wants `sys.path.insert(0, "../logit-kld"); from inspect import read_file`. That silently replaces Python's own `inspect` module for the whole process, and the symptom lands wherever some library imports `inspect` internally, not where the mistake was made — or, if something imported the real one first, as a confusing `ImportError: cannot import name 'read_file'`. Load it by path instead (`importlib.util.spec_from_file_location("lkld_inspect", ...)`), as `nano-glm/gate.py` does. Same care applies to any future script named after a stdlib module.

- **A half-TB process takes minutes to die, and the link error blames the wrong thing**: rebuilding nano-glm while a `moe-server` from an earlier session was still running failed with `LINK : fatal error LNK1104: cannot open file 'bin\moe-server.exe'`. `Stop-Process -Force` returned immediately and the *next* build failed identically — the process was still there with a 32 GB working set, unmapping 583 GiB of views. It took ~4 minutes to actually exit. LNK1104 reads as a stale lock or an antivirus scan; on this machine, with these models, it usually means a still-running server. Check `Get-Process moe-server` first, and `Wait-Process -Id <id> -Timeout 600` rather than retrying the build in a loop. Corollary: stop the backend before rebuilding, not after the link fails.

- **`GetLogicalProcessorInformationEx` records must be walked by `info->Size`, not `sizeof()`**: counting physical cores on Windows by iterating `SYSTEM_LOGICAL_PROCESSOR_INFORMATION_EX` with a `off + sizeof(...) <= len` loop bound reported **15 cores on a 16-core** CPU. The struct is a union whose declared size is dominated by `GROUP_RELATIONSHIP` and is larger than a real per-core record, so the final entry falls outside the bound and is dropped. Correct form is `for (off = 0; off < len; off += info->Size)`. The failure is quiet and plausible — an off-by-one core count still runs, just slower, and prints a believable number — so print detected physical *and* logical counts (nano-glm's header line does) and sanity-check them against `Get-CimInstance Win32_Processor`.
