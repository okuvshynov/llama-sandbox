# CLAUDE.md

## Mistakes

These are the mistakes which were encountered in the past while working on this project. You MUST try hard to avoid these mistakes in the future.

- **Documentation drift during /commit**: When using `/commit`, README.md and TECHNICAL.md were not checked for staleness. Over multiple commits (file format changes, new subcommands, BF16 reference migration, prompt restructuring), the docs fell far behind — referencing old file formats (v3 trace files instead of stats files), old subcommand interfaces (`compare -a -b` instead of `compare -f`), stale prompt counts (12 instead of 19), and Q8 as reference when BF16 was adopted. Fix: during `/commit`, always check if key documentation files (README.md, TECHNICAL.md) reference concepts that were changed in the committed code. If the commit changes file formats, CLI interfaces, model configurations, or experiment methodology, update the docs in the same commit.

- **Piping long-running commands through `tail -N`**: Smoke / sweep commands like `python validation_bench_openai.py ... 2>&1 | tail -20` were used to keep the displayed output short. The downside: while the run is active you can't see streaming progress (turn-by-turn lines); and if something interesting happened in the discarded prefix, you have to rerun the whole thing to recover it. Fix: capture full output by redirecting to a file (or use `run_in_background: true` and read the output file the harness already creates), then `head`, `tail`, or `grep` against the saved file as needed. This preserves both progress visibility and the full transcript for later inspection.

- **Scoring-contract bugs ship without scorer unit tests**: Two scoring loopholes in validation-bench's contract evolution (vb_version 0.0.7 → 0.0.8 → 0.0.9) were missed in review and only surfaced via manual reproduction during ad-hoc validation. The 0.0.7 exit-code rule credited any timeout on an invalid input as a correct rejection (`rc != 0 → TN`); the 0.0.8 verdict-only rule credited "print right verdict, then crash" as a success. In both cases the "obvious" mental model held, but the rule's full input cross-product had untested holes. Fix: any change to `run_tests` scoring or `_fail_detail` formatting needs a test that exercises (right/wrong verdict) × (clean/dirty exit) × (timeout/crash/signal/no-output). The `_FakeSandbox` stub in `test_validation_bench.py` (no docker, no live model) makes adding scorer tests cheap — the bar to extending coverage when the contract changes should be near zero.

- **Alpine-based env Dockerfiles must `apk add coreutils`**: busybox's `timeout` (the alpine default) leaks one zombie process per invocation under the harness's `sh -c "timeout -s KILL Ns ./solution"` wrapper. The zombie is reparented to PID 1 (`sleep infinity`), which doesn't reap. With `--pids-limit=256`, a 678-test corpus saturates the cgroup at test ~#250; every subsequent test fails with `timeout: vfork: Resource temporarily unavailable`, which the harness records as `no output (exit=1)`. Symptom in the data: confusion matrices clustered like `TP=0, FN=205, FP=220, TN=253` — perfectly tracking the alphabetical test order in `tests.jsonl` (invalid first, valid second), with the cgroup saturating between the two halves. *Not* a model failure, *not* a parser bug — purely the combination of alpine + `--pids-limit=256` + 678 tests + busybox timeout. Verified opus's toml-1.0-zig validator scores MCC=+1.0000 once GNU coreutils' `timeout` (`apk add coreutils`) replaces busybox's. Same fix applies to any future alpine-based env (currently `data/envs/zig/`, `data/envs/go/`). Debian-based envs (cpp17, lua, erlang) ship GNU coreutils by default and are unaffected. The `validation_bench_lib.py:569` "Go runtime maps goroutines to OS threads" hypothesis was misdiagnosing this same root cause for Go.
- **llama.cpp op offload to the AMD-Metal GPU silently NaNs logits at batch ≥ 32 (Intel Mac Pro)**: On this Mac Pro 7,1 (AMD Radeon Pro Vega II Duo via Metal), llama.cpp's default `op_offload` ships large-batch host ops to the GPU once a decode batch reaches 32 tokens — even with `-ngl 0` and all weights on CPU. For GLM-5.2 Q6_K this produced NaN logits for *every* position of the batch; there is no error, no warning, and small batches on the identical setup are clean, so smoke tests pass and the corruption only appears when a longer sequence is decoded in one chunk (logit-kld's rescore at `-b 512` caught it; collect's 14-token prompt + 1-token generation steps never crossed the threshold). Diagnosis that separated the suspects: batch 16 chunks → clean (threshold confirmed); rebuild with `GGML_METAL=OFF`, batch 512 → clean (Metal offload guilty, Accelerate BLAS innocent). Fix adopted in logit-kld: force `GGML_METAL OFF` in the subproject's CMakeLists so the tools are CPU-only by construction. Watch-out for any other llama.cpp-based tool or server run on this machine: results computed with default build settings and batches ≥ 32 tokens are suspect; check for NaN/garbage logits before trusting them.

- **ggml logits are only bit-reproducible within one toolchain AND one thread count**: "bit-identical" is never a property of a model + token ids alone — it is a property of a *run configuration*, and two knobs beyond the known batch-shape one silently change the numbers. (a) **Thread count**: ggml partitions matmul work by `n_threads`, so the summation structure changes with `-t`. Measured on GLM-5.2 UD-Q6_K: `-t 16` vs `-t 32` produce different logits, while two runs at a fixed count are bit-identical even across cold/warm page cache. (b) **Compiler**: llama.cpp disagrees with *itself* by 8.85e-3 mean KL / 96.67% top-1 between an Apple-clang macOS build and an MSVC Windows build — same Xeon W-3245, same AVX-512 level, same llama.cpp commit, same CPU_REPACK fallback, same token ids. Cause is FP contraction in the plain-C kernels (Apple clang contracts `a*b+c` into FMA by default; MSVC at `/fp:precise` does not), not ISA. Both effects land at the *same order* as the batch-shape noise floor (~1e-2) and as the Q6_K_XL→Q6_K quant gap (6.7e-3) this tooling exists to measure, so either one can be mistaken for a real model difference or for a port bug. Consequences: every tool in a verification toolchain must share one thread-count default or an A/A between two of them measures thread noise (hence `logit-kld/src/cpu_topology.h`, shared by collect/rescore/nano-glm); each platform needs its OWN reference files; and baselines collected before 2026-08-06 used `hardware_concurrency()` = 32 logical, so comparing against them on this machine needs an explicit `-t 32`. When a KL==0 gate fails, check the run configuration before suspecting the code.

- **Verify the model bytes before debugging the code — and know that a hash right after a copy may only be checking the page cache**: a bit-exact gate that had passed for two days started failing by ~8.6e-04 mean KL (no token changes, below every documented noise floor, but enough to break byte-comparison). An hour went into eliminating source changes, ggml version, compiler flags, thread count, OpenMP team size and llamafile sgemm tiling — all identical, all innocent. The cause was two of fourteen GGUF shards being corrupt on disk. `sha256` against a known-good copy on the other machine found it in twenty minutes; **hashing the inputs should have been the first move, not the last.** Specifics worth keeping: (a) the corruption was ~1.9 KB spliced into two 40-50 GB files, which still had the correct size, parsed as valid GGUF, loaded without complaint and produced fluent text — nothing about it looked like corruption; (b) **the page cache masked it for a full day** — the copy wrote through cache, so runs that day read the still-correct cached pages and only a reboot exposed the bad bytes on disk, which also means a `Get-FileHash` immediately after a large copy verifies the cache, not the platter (verify again after a reboot, or bypass the cache); (c) **MoE routing made the damage position-dependent** — corrupt expert weights only perturb tokens that route to them, so some positions stayed bit-exact while others drifted, a pattern that looks nothing like a compiler or threading difference and which is a strong tell for bad weights; (d) the corrupt bytes were a *structured* in-memory descriptor table (repeating 8-byte records, 2 MiB stride, mostly not sector-aligned), i.e. a Windows writeback-DMA bug handing down the wrong source address — not bit rot, and invisible to the storage error log and `chkdsk`, both of which stayed clean because nothing actually failed. (This entry used to claim WHEA was clean too. It was not — nine corrected-memory-error warnings sit in the System log between 2026-08-02 and 2026-08-07, eight of them at the *same* physical address. Corrected errors deliver correct data, so they are not the mechanism, and a 2 MiB-stride descriptor table is not a bit flip — but the log was never actually checked, and "the hardware logs are clean" was asserted rather than verified. See `checksums/README.md`, "The memory subsystem is degrading".) Manifests and the diagnostic tools (`chunk_hash.py`, `bindiff.py`) live in `checksums/`; the damage shape is what distinguishes a driver bug from a hardware one, so diff a corrupt file against a good copy *before* overwriting it. Also: `Get-Volume` reports `HealthStatus: Warning` / `OperationalStatus: Full Repair Needed` and `FileSystemType: Unknown` for healthy exFAT volumes — it survives a clean `chkdsk`, so do not read anything into it.

- **On Windows, mmap-backed weights make timings unreproducible at half-TB scale**: benchmarking GLM-5.2 (582.87 GiB) with stock `llama-bench` on the Mac Pro under Windows returned tg32 = 1.84 ± 0.02 t/s in one invocation and 1.04 ± 0.29 in the next — same binary, same model, same thread count, differing only in standby-list state. `--load-mode none` (weights read into ordinary allocated memory) gives a steady 1.90 ± 0.08. macOS on the identical machine shows no such spread (± 0.00-0.01 across 5 reps). Consequences: never trust a single mmap-backed timing on Windows — re-run it, or use `-lm none`; and when a run's throughput looks anomalous, suspect paging before compute. This also explains why harness-style runs (collect/rescore/nano-glm, which page the model in *during* the measured window) read ~1.3 t/s against `llama-bench`'s ~1.84 warmed. Related trap: quoting a 2-rep benchmark at all — a 2-rep prefill sample suggested a 2x SMT gain that 5 reps flatly contradicted. Use `-r 5` and pp128+ on this model; short prefills (pp64) are dominated by paging noise (±27%). **Amendment (2026-08-12): `-lm none` removes that variance only *within* one invocation, not across loads.** Benchmarking DeepSeek-V4-Flash with `-lm none -r 5`, the same configuration — same flags, same model, same per-device buffer sizes to the MiB, same graph-split count — decoded at 3.58 ± 0.02 on one load and 3.94 ± 0.06 on the next: **10% load-to-load against within-run sds of 2-6%**. So `-r 5` reports the spread of five reps *inside* one process and says nothing about the spread between processes, and the second number is the larger one. Consequence for any sweep where each row is its own invocation — which is every `-ngl`/`-ncmoe`/`-ts` sweep, because those change what is allocated where and force a reload: **differences below ~10% between rows are not evidence**, and at least one configuration must be repeated on a second load before an ordering is quoted. The cheap discipline is to re-run the row you are about to call the winner; that one extra load is what turned a clean-looking monotone trend into a band.

- **The page cache corrupts in BOTH directions on this machine — a buffered hash cannot tell you which**: the 2026-08-07 entry below says the cache masked corrupt *disk* bytes. On 2026-08-10 the reverse happened: `gate.py smoke` failed on a model whose **disk copy was perfect**, because a page-descriptor table had been spliced into *cached pages* of a read-only mapping. `Get-FileHash` reads through the cache, so it reported the file BAD; `checksums/hash_nocache.ps1` (FILE_FLAG_NO_BUFFERING) matched the manifest exactly. Remedy is a **reboot, not a 49 GB restore** — the opposite of last time. Both failures produce the identical symptom, so the deciding test is the unbuffered hash: disk == manifest means reboot; disk != manifest means restore from the other machine. Two further consequences: size and mtime are unchanged (nothing wrote to the file), so a provenance check cannot see it; and a fault that can scribble into `PAGE_READONLY` cached pages can hand wrong weights to *any* long-running process here without the file ever changing. The tell is always the same — a deterministic, position-dependent divergence with no token changes and KL well below every documented noise floor (1.35e-04 mean here), because MoE routing means only tokens that route through the damaged expert move. `checksums/scan_splice.py` finds the signature (`f1 04 XX XX 07 00 40 00`, 2 MiB stride) in a single file with no reference copy, which is what makes the diagnosis possible before deciding whether to overwrite anything. Full record: `checksums/shard02-cache-corruption.txt`.

- **Two PowerShell habits that silently truncate a long run**: (a) `... | Select-Object -First N` closes the pipeline as soon as it has N objects, which **terminates the upstream native process** — a `python study.py | Tee-Object -FilePath out.txt | Select-Object -First 46` exited 255 and left `out.txt` with 45 of its 101 lines, looking exactly like a crash in the script. Redirect to a file and read it afterwards (`> out.txt 2>&1`, then `Get-Content`), or use `Select-Object -Last`, which has to consume everything anyway. (b) PowerShell does **not** glob for native commands: `python tool.py results\*.trace` passes the literal string and the tool fails on a filename containing `*`. Expand first — `$t = (Get-ChildItem results\*.trace).FullName; python tool.py @t`. Both failures point at the script rather than the shell, which is what makes them expensive.

- **Measure the machine's ceiling separately from the application, or you will attribute the shortfall to whatever mechanism you had in mind**: nano-glm decode sustains 75.4 GB/s against 140.8 GB/s of theoretical DDR4-2933 (12x64 GB, 6 channels, 2933 configured), and the gap sat in the plan for weeks as a huge-pages story — 31.5 MB per expert against a 1536-entry L2 TLB, and Intel's L2 streamer not prefetching across a 4 KiB page boundary, so streaming one expert restarts it ~7,700 times instead of ~15. Plausible, and wrong. A 40 GB probe with no model (`nano-bench --pages`) measured **4 KiB pages already reaching 100.6 GB/s at 16 threads and 102.8 at 32**, with shuffled expert-sized blocks matching a flat sequential sweep (98.9 / 106.9) — so the scattered `mul_mat_id` access pattern costs nothing and page size cannot explain the shortfall. What the probe did establish is that the model runs at ~75% of what its own access pattern allows, i.e. roughly a quarter of decode is dequantization and per-node barriers rather than memory movement, which also retires the "expert FFN is ~95%+ memory movement" rule of thumb. Cost of finding out: minutes, versus a non-mmap loader rewrite plus 583 GiB read per run plus 583 GiB locked non-pageable. Probe the mechanism at small scale before building the thing that exploits it.

- **On Windows, non-ASCII command-line arguments are mangled before `main()` runs**: the CRT builds `argv` by converting the wide command line through the *ANSI* code page, cp1252 on this machine. So `-p "façade"` arrives as the single byte `0xE7` where UTF-8 would be `C3 A7`, and anything outside cp1252 — every CJK character — arrives as `?`. Nothing errors: a byte-level tokenizer happily tokenizes the mangled bytes and returns ids that are simply wrong. Symptom that identifies it: **every ASCII case passes and every non-ASCII case fails**, which is an encoding problem, not a logic one — `nano-glm/tokenizer_check.py` showed 16/28 cases agreeing with llama.cpp, all 12 failures non-ASCII, and 28/28 after the fix with no change to the tokenizer at all. Fix is `GetCommandLineW()` + `CommandLineToArgvW()` + `WideCharToMultiByte(CP_UTF8, ...)` (shell32 is already in CMake's default link libraries), plus `SetConsoleOutputCP(CP_UTF8)` so generated UTF-8 does not render as mojibake — see `utf8_args()` in `nano-glm/apps/nano-chat/main.cpp`. Prefer a file argument over `-p` for any text that matters; a file has no code page and no length limit.

- **`logit-kld/inspect.py` shadows a stdlib module — never put that directory on `sys.path`**: it is the reference reader for the lkldtopk format, so a new tool naturally wants `sys.path.insert(0, "../logit-kld"); from inspect import read_file`. That silently replaces Python's own `inspect` module for the whole process, and the symptom lands wherever some library imports `inspect` internally, not where the mistake was made — or, if something imported the real one first, as a confusing `ImportError: cannot import name 'read_file'`. Load it by path instead (`importlib.util.spec_from_file_location("lkld_inspect", ...)`), as `nano-glm/gate.py` does. Same care applies to any future script named after a stdlib module. **It is not only `import` that trips this — merely *running* a script whose CWD is `logit-kld/` does.** Python puts the script's own directory at `sys.path[0]`, so a plain `python mytool.py` from there breaks on `import argparse`, because argparse imports dataclasses which imports inspect. The failure is spectacular and misleading: a traceback deep inside `argparse.py` about `module 'inspect' has no attribute 'signature'`, for a script that never mentioned inspect. Python 3.14 helpfully names the culprit in the message; older versions do not. Keep new Python tools *out* of `logit-kld/` — `nano-glm/` is the usual right home — or strip the script's directory from `sys.path` before the first non-builtin import.

- **A half-TB process takes minutes to die, and the link error blames the wrong thing**: rebuilding nano-glm while a `moe-server` from an earlier session was still running failed with `LINK : fatal error LNK1104: cannot open file 'bin\moe-server.exe'`. `Stop-Process -Force` returned immediately and the *next* build failed identically — the process was still there with a 32 GB working set, unmapping 583 GiB of views. It took ~4 minutes to actually exit. LNK1104 reads as a stale lock or an antivirus scan; on this machine, with these models, it usually means a still-running server. Check `Get-Process moe-server` first, and `Wait-Process -Id <id> -Timeout 600` rather than retrying the build in a loop. Corollary: stop the backend before rebuilding, not after the link fails.

- **`GetLogicalProcessorInformationEx` records must be walked by `info->Size`, not `sizeof()`**: counting physical cores on Windows by iterating `SYSTEM_LOGICAL_PROCESSOR_INFORMATION_EX` with a `off + sizeof(...) <= len` loop bound reported **15 cores on a 16-core** CPU. The struct is a union whose declared size is dominated by `GROUP_RELATIONSHIP` and is larger than a real per-core record, so the final entry falls outside the bound and is dropped. Correct form is `for (off = 0; off < len; off += info->Size)`. The failure is quiet and plausible — an off-by-one core count still runs, just slower, and prints a believable number — so print detected physical *and* logical counts (nano-glm's header line does) and sanity-check them against `Get-CimInstance Win32_Processor`.

- **A comparison that silently covers less than the tensor is worse than no comparison, and `zip` is how it happens**: `logit-kld`'s `dump` truncates each tensor to `--max-elem` (4M by default) while writing the full `ne`, so two records can agree on shape and carry different amounts of data. `dump_inspect.py` compared them with `zip(a, b)`, which stops at the shorter — reporting `0.0000e+00` and "134 compared, 0 missing, 0 shape mismatches" for a tensor it had checked **one third of**. The coincidence that made it dangerous: at 384 tokens `attn_raw` is 32768x384 = 12.6M elements, the 4M cut lands at exactly token 128, and 128 is this model's sliding-window width — so the truncation stopped precisely where a causal mask and a sliding-window mask start to differ. A wrong mask passed, twice, in both directions. It surfaced only because a *negative control* (deliberately breaking the mask) also passed; comparing the two runs against each other showed 7.1e+00, which is impossible if both equal the reference. Fixes: `dump_inspect` now reports `PARTIAL n vs m` and fails, and any long-sequence dump needs an explicit `--max-elem` (1.5 GB for three layers at 384 tokens — the cost of a check that actually covers the tensor). Generalisations worth keeping: **a truncating reader must compare lengths, not just shapes**; when a negative control passes, do not conclude the effect is absent, conclude the *harness* is broken and go find out how; and two green results that contradict each other are one datum, not two.

- **`ggml_clamp` is silently in-place, so the tensor feeding it is unreadable after the graph runs — and the corruption is invisible everywhere the clamp did nothing**: `ggml_clamp` returns `ggml_view_tensor(ctx, a)` and writes through it (ggml.c), unlike almost every other op which has an explicit `_inplace` variant. A dump that reads tensors *after* `ggml_backend_graph_compute` therefore sees post-clamp values under the pre-clamp name. llama.cpp never notices because its `cb_eval` fires the moment each node is computed, before the clamp runs; a port that reads at the end does not have that luxury. What makes it nasty is the failure *shape*: a clamp only changes values past its limit, so deepseek4's `ffn_moe_gate` agreed exactly for four layers and then differed in **two elements out of 4.7 million** in layer 5 — both above the 10.0 limit — with `ffn_moe_gate_clamped` and everything downstream still matching. The tell is that the wrong side reads exactly the limit (`mine=+10.000000, ref=+10.556865`): not a rounding difference, a different quantity. Fix is a `ggml_cont` taken before the aliasing op (`ds4_cb_call_pre_inplace` in `lib/models/deepseek4/moe_block.h`), not a flag — `GGML_TENSOR_FLAG_OUTPUT` does not help, because `ggml_gallocr` correctly refuses to *reuse* an output's buffer but the view writes through regardless. Applies to every clamp input in the graph, including `ffn_moe_weights_sum` where the 2^-14 floor almost never triggers. General rule: before dumping a tensor for later comparison, check whether any consumer aliases it, and copy if so.

- **A reference can do work that changes nothing, purely to keep its graph shape stable — and a port that skips it cannot be compared tensor by tensor**: llama.cpp pads deepseek4's ratio-4 compressor to a fixed block count with **dummy blocks** (`llama-kv-cache-dsv4.cpp:546`), so that every ubatch of a given size builds the same graph and can reuse its allocation. A dummy folds the current token with itself, writes to the last cache cell — which no mask ever makes visible — and is discarded. Arithmetically it is a no-op; in the *tensor list* it is a whole compressor's worth of intermediates. Skipping them is therefore correct and unverifiable at once: at ratio 4 a decode step closes a real block only one time in four, so the reference emitted six tensors named `norm-2` per step where the port emitted four, every later occurrence paired against the wrong one, and the comparison reported dozens of large differences that were all alignment. The symptom to recognise: **shape mismatches on a repeated name, mixed with huge relative diffs, while a different layer of the same model is perfectly exact** — that is misalignment, not arithmetic, and the fix is upstream of any value. Diagnose it by extracting the ordered list of one repeated name's shapes from both dumps and finding the first index where they diverge; the pattern of what the reference has and you do not names the missing work directly. Note the guard is per-cache — the ratio-128 compressor is *not* padded — which is why one layer kind agreed and the other did not.

- **"Uncomparable by construction" was a claim about my harness, not about the reference — and it was wrong**: eleven of deepseek4's tensors (`csa_raw_k`, `csa_comp_k`, `csa_k_all`, `csa_lid_kq_mask`, `lid_score_masked`, `lid_top_k`, `csa_top_k_mask`, and the `hca_*` equivalents) were excluded from the comparison across three commits, with the reasoning that they are views of a *padded* KV cache — llama.cpp turns 384 tokens into 512 rows and 96 compressed blocks into 256 — so a view sized to the data can never equal one sized to the cache, and the padded tail holds whatever the buffer held. Every sentence of that is true and the conclusion did not follow: the port was free to size its own cache the way llama.cpp does. Once it did (`get_n_kv`'s "at least 256, rounded up to 256, capped by the cache size", plus a comp cache with the same 256 floor so the cap does not bite), **all eleven compare bit-exactly**, padded cells included, because both sides zero their buffers. Coverage went from 394 tensors to 416 and the exclusion list from eleven names to one. The lesson generalises past this project: when a reference artifact "cannot" be compared, the question is whether it is unreachable *in principle* or merely unreachable *from where you are standing* — geometry chosen by the thing you are imitating is usually the second. The remaining exclusion is `node_`, which is unreachable in principle: ggml numbers anonymous nodes per graph, so two implementations that agree perfectly still number them differently. And the rest of the original entry stands — never add a name to `--exclude` because it disagrees, and never teach the tool to skip shape mismatches, because both hide real failures.

- **PowerShell's `>` writes a UTF-8 BOM, and `atoi` turns it into a silent 0**: generating a token-id file with `python -c "..." > tokens.txt` produced a file starting `EF BB BF 31 30 30 30`. `logit-kld/dump` parsed the first id as **0** — a perfectly valid token — so the run succeeded on a prompt whose first token was not the one intended, while `nano-glm/ds4-port` used `strtol` and aborted on the same file. The asymmetry is the tell: one tool refusing a file the other accepts means the *file* is wrong, not the tool. Both readers now strip a leading BOM, and files meant for them are written with `io.open(..., encoding="ascii")` from Python rather than through a PowerShell redirect. Note the general shape: `atoi` has no error channel, so any place it parses external input converts malformed data into a plausible value.

- **`GGML_CPU_REPACK` is a fourth knob that changes the logits, and it is per-quant-type AND per-ISA — so it stays invisible until the model that trips it**: the entry below lists thread count, compiler and batch shape as the things that must match for two ggml runs to agree. Weight repacking is a fourth. llama.cpp defaults `GGML_CPU_REPACK=ON`, which rewrites quantized weights into a blocked layout at load (`load_tensors: CPU_REPACK model buffer size = 140352.00 MiB`) and runs a different GEMM against them. nano-glm mmaps weights exactly as they sit in the file — a 583 GiB model cannot afford a converted second copy, and neither can the remote-expert design — so it can never match a repacked reference. This did not surface across two years of GLM-5.2 work because the repack table is gated on *both* the quant type and the ISA: Q6_K only repacks under NEON, so on this x86 machine nothing was ever converted and `gate.py llamacpp` reached KL == 0 honestly. DeepSeek-V4-Flash's MXFP4 experts repack under AVX2, which this machine has — 140 GiB of `mxfp4_8x8`, and ~1e-6 absolute (up to 1.0 *relative*, on near-cancelling values) on every routed-expert matmul. **The signature is what identifies it: exactly the `mul_mat_id` tensors disagree and every plain `mul_mat` — including the shared expert, which uses the same loader and the same activations — is bit-exact.** A graph bug does not respect an op-type boundary that cleanly. Fix adopted: `set(GGML_CPU_REPACK OFF)` in `logit-kld/CMakeLists.txt`, beside the existing METAL/BLAS/LLAMAFILE forcing. Consequence to keep in mind: that makes the *reference* slower, so a performance comparison against llama.cpp needs a build without that line, while only the correctness comparison wants it. Check `grep "repack: repack tensor"` on a reference log before trusting a new model's bit-exactness.

- **A mathematically-invariant wrong graph hides inside the precision noise floor — and only the *unnamed* reference nodes can find it**: porting deepseek4's layer-0 attention left `attn_raw` off by 4.0e-03 (~7e-4 relative, i.e. F16 epsilon) with all fourteen tensors feeding it bit-identical. Everything about that reads "remaining precision difference", and two precision hypotheses were tried and correctly rejected before the real cause surfaced: **the port applied a Hadamard rotation to q and k that llama.cpp does not apply to this model**. `llama_kv_cache::build_input_k_rot` only builds a rotation when `attn_rot_k` is set, which needs a **quantized** KV cache (`ggml_is_quantized(type_k)`, `llama-kv-cache.cpp:319`); the default cache is F16, so the reference log says `attn_rot_k = 0` for every 512-wide cache and rotates nothing. Only the 128-wide lightning-indexer cache rotates. Two lessons, both general. (a) **An orthonormal, self-inverse transform applied and undone changes no mathematics, only rounding** — so a structurally wrong graph lands in exactly the band you would write off as F16 noise, and "the magnitude looks like precision" is evidence about magnitude, not about cause. Suspect the graph before the kernels whenever the neighbours are *exactly* zero: real precision drift usually accumulates upstream too. (b) **Name-filtered dumps cannot see between two named tensors.** llama.cpp `cb()`s some of what it builds; the difference sat in the gap, where a `--layer`/`--name` filter has nothing to show. `dump --max-records 150` writes every node in graph order, named or not, and the answer was immediate and unambiguous: the node feeding flash-attention is called `q-0 (view) (permuted)` — a view of `q` itself, with no matmul in between. When a port's difference is localised between two exact tensors, dump the reference's raw node list *first*; it is one run and it either shows the missing op or rules the whole class out. (`nano-glm/lib/models/deepseek4/graph.h`, `logit-kld/src/dump.cpp` `--op` / `--max-records` / `-T`.)

- **A ggml *view* marked GGML_TENSOR_FLAG_OUTPUT is not readable after the graph runs**: `ggml_gallocr_alloc_graph_impl` frees a view's **parent** once the view has no children left, and the OUTPUT flag it tests belongs to the node being freed — the flag on the view protects nothing, so a later op is handed the same bytes and the read-back gets whatever that op left there. This is the same trap `run_router` hit in moe-server (fixed there with `ggml_cont` on both ids and weights) and it recurs every time a dump is added, because the natural thing to name is the tensor the code is already holding, which is often a `ggml_reshape`/`ggml_view` result. Fix is a copy taken at the right point in graph order (`ds4_snapshot` in `nano-glm/lib/models/deepseek4/graph.h`), not a flag. Related, and separately expensive: **emission order is part of a per-tensor comparison's contract**. llama.cpp reuses names (`norm` appears three times in one layer) and `dump_inspect.py` pairs repeated names by position, so adding a `ggml_build_forward_expand` for a dump copy pulled a whole subtree in front of another and produced two `SHAPE ... vs ...` rows on tensors whose *values* were bit-identical. Expand deliberately, in the reference's order.

- **Four ways a "the GPU differs by X" measurement lies, all hit in one afternoon**: bringing up nano-glm's Vulkan expert path (`nano-glm/vk_check.py`, PLAN.md step 3 increment 2) produced four plausible numbers that were each wrong for a different reason, and every one of them would have shipped as fact without a control. (a) **No same-arithmetic control** — CPU-vs-GPU showed KL max 9.6e-3, which looked like GPU error; running the *identical* split onto a second **CPU** device showed 7.6e-3, so most of it was the partition (a token's 8-term expert sum reassociated into (7)+(1)), not the driver. Never attribute a difference to the new component until the old component has been made to do the same new thing. (b) **A floor that could not vary** — the reproducibility floor compared `-b 512` against `-b 16` on a **14-token** prompt, so both prefilled in one chunk and it reported a flat `0.0000e+00` that read as a perfectly deterministic GPU and was literally the same run twice. A control that structurally cannot fail is worse than none, because it manufactures confidence. (c) **Free generation instead of fixed ids** — each configuration got the same *prompt* and generated its own continuation, so 4 of 18 comparisons produced no number at all ("token sequences differ"), including one with **both sides on the CPU**: a reassociation flipped one greedily-sampled token and the sequences parted. Numerical divergence changes what an LLM generates, so it cannot be measured over free generation; score a fixed id sequence (`-T <ids> -n 0`). (d) **Saturation** — raising the GPU's share of the work 5.5x (0.8% -> 4.37% of routed pairs, measured, not estimated) moved *no* figure, and the no-GPU shape floor sat in the same 4e-3..9e-3 band. 75 layers amplify any perturbation to one ceiling, so end-to-end logit KL cannot distinguish a subtly wrong kernel from a correct one; it can only establish determinism. Measure at the layer, not at the logits. Corollary worth remembering on its own: **MoE routing turns continuous differences into discrete ones** — the CPU control assigned 478 pairs to its split device where the GPU assigned 472, same k and same placement, because a perturbation flipped an argmax.

- **`op_offload` makes a GPU-enabled build *slower* than a CPU-only one at `-ngl 0`, and the graph-split count is the tell**: llama.cpp built with `GGML_VULKAN=ON` prefilled DeepSeek-V4-Flash at **5.37 t/s against the CPU-only build's 17.99** — same source, same flags but the one, and **nothing deliberately offloaded**. The mechanism is two lines. `ggml_backend_sched` offers any op whose *weights sit in a host buffer* to a higher-priority backend (`ggml-backend.cpp:959`), and the Vulkan device accepts once the op's batch reaches `op_offload_min_batch_size`, default **32** (`ggml-vulkan.cpp:18511`; override `GGML_OP_OFFLOAD_MIN_BATCH`). DeepSeek-V4 has two ops Vulkan cannot run at all — `DSV4_HC_COMB` on every layer and `LIGHTNING_INDEXER` on the ratio-4 layers, both present in CPU, CUDA and Metal — so every accepted op is dragged straight back and the prefill graph shatters into **1780 splits**, against **1** at batch 1, which is below the threshold and is why decode looked fine. `-nopo 1` / `--no-op-offload 1` recovers it exactly (17.96 ± 0.14). Three things to carry. (a) **A GPU-enabled build is not a superset of a CPU-only one** on any model with backend-specific ops; do not assume one binary can serve both, and do not read `-ngl 0` on a GPU build as a CPU baseline — the honest control is a separately-built CPU-only binary. (b) **`sched_reserve: graph splits = N` is the diagnostic**, and it tracked prefill inversely across every configuration measured (1780 splits → 5.37 t/s, 10 splits → 16.68), so record it beside any timing rather than only the timing. (c) It is the same scheduler policy as the Metal entry above, where it produced NaN logits instead of a slowdown — one mechanism with two faces, and the batch-32 threshold identifies both, so a result that changes character at batch 32 should point here first.

- **Freeing a ggml compute buffer every chunk costs twice, and the second cost lands somewhere a phase timer cannot attribute it**: deepseek4's `eval_chunk` built a `ggml_gallocr` per chunk and freed it at the end, which is the obvious shape for a function that also builds its graph per chunk. Profiling put **`free` at 37 ms/chunk — the largest host-side cost, and four times the 9 ms `alloc` it undid**; `ggml_gallocr_free` releases the compute buffer, and the next chunk re-commits it. Keeping the allocator in the state removes that, and `ggml_gallocr_reserve` reallocates only when a graph needs *more* than the current buffer, so after the first (largest) chunk a decode step pays neither. **The half that matters more was invisible to the timer**: an A/B of the two binaries, alternating, three runs each, showed `compute` **45 ms/chunk lower** with the allocator reused — against 38 ms/chunk removed from `alloc`+`free` directly — with no overlap between the two sets of three. Releasing the buffer means the next chunk soft-faults it back in on first touch, and those faults are billed to `ggml_backend_graph_compute`, not to the free. Net +13.9% decode, output byte-identical. Three things to carry: (a) **per-chunk allocator churn is worth checking in any ggml-based loop**, and the tell is `free` costing more than `alloc`; (b) **a phase timer attributes work to where it is billed, not to what caused it**, so a phase that "should" be constant getting faster is a result, not noise — it means the change moved work out of that phase; (c) instrumentation and A/B are not substitutes — the timer found the suspect and could only see half the effect, and the A/B measured the whole thing but would never have pointed at an allocator.

- **Before believing an A/B, prove the treatment was switched on — "no difference" is what a disabled treatment looks like**: the `moe-serv` handshake check ("a backend that claims nothing must be invisible") reported *identical* three times in a row while testing nothing at all. (a) The first run set only `GGML_BACKEND_PATH`, and `llama_backend_init` calls `ggml_backend_load_all()` **only when `ggml_backend_reg_count()` is zero** — the statically linked CPU backend had already registered, so the variable was never read and the library never loaded. (b) The second added `-ot`, but through `cmd /c "... -ot \"\.ffn_(up|down)_exps=MoE\""`, where `|` is a cmd pipe: the argument never reached the exe, which then ran a perfectly ordinary comparison of stock against stock. (c) A later attempt aborted on a *false* negative, because the guard grepped for the loader's `load_backend` line and `llama-completion` filters INFO at default verbosity — the backend was loaded, the evidence was simply not in the capture (`-v` fixed it). The general shape: **an A/B where the treatment silently fails to apply produces a clean, plausible "no difference", which is also the result you were hoping for.** So assert engagement positively and separately from the outcome — a line in the log, a buffer that appears, a counter that moves — and make the harness *abort* rather than compare when that assertion fails. This is the same family as the "control that cannot vary" entry above, arriving from the other side: there the control was degenerate, here the control was fine and the treatment was absent. Two smaller ones from the same afternoon, both already written down elsewhere in this file and done anyway: piping a native run through `Select-Object -First N` killed it at exit 255 mid-measurement, and `*>` redirection wrapped native stderr in PowerShell ErrorRecords, corrupting both captures and hiding the very line the guard was looking for.

- **A deliberately architecture-neutral fast path will silently omit an architecture-specific op, and the gate that should catch it may never execute that path**: `moe-server`'s `run_device_compact` — the path a device takes when it holds only *some* experts — moves weights and calls `mul_mat_id` and knows nothing about which model it serves. That neutrality is the right design and it has exactly one failure mode: an op the architecture needs that the neutral path does not have. deepseek4 clamps its SwiGLU at ±10.0 before the split; `run_device_compact` built `mul_mat_id -> swiglu_split` with nothing between, correct for glm-dsa and wrong for deepseek4. `swiglu_clamp_exp` appeared **once** in the whole file, in the *other* path. What let it live for four commits is the shape of the test: **`gate.py rpc` starts a server with no `--gpu-experts` and no `--cpu-experts`, so every expert lives on device 0 and takes the non-compacted path — the gate's server configuration never reaches the code the gate exists to check.** Every measurement taken with `--gpu-experts 240` therefore ran 240 of 256 experts unclamped. Three things to carry. (a) When a second architecture is added, grep the neutral layer for *everything* the model-specific block does between the same two ops, rather than trusting that "it only moves weights"; the diff that matters is ops the neutral path lacks, not ops it has. (b) **Ask which configuration the gate actually runs**, not just which test names pass — a green suite whose fixture avoids the risky path is worse than no test, because it reads as coverage. (c) The right check here was `--compare` on a split configuration all along, and it had never been run for the second architecture; use `--cpu-experts` rather than `--gpu-experts` so both sides share arithmetic and any residual is the graph. Measured either way, with only **12.67%** of pairs on the split device: **max |split-cpu| 2.241e+02 and rel RMS 5.598e-02 without the clamp, against 1.221e-04 and 1.873e-08 with it** — six orders of magnitude, so this was never subtle and one run at any point in four commits would have found it. (d) **Do not estimate a bug's blast radius from a note about a different tensor.** This entry first claimed the missing clamp "moves values slightly", reasoning from the `ggml_clamp` entry above, where the limit was exceeded by 2 elements in 4.7 million. That was a measurement of `ffn_moe_gate` in one layer at one length, and the routed-expert output behaves nothing like it: 5.6% RMS is pervasive, not rare. Cost of the wrong guess was reporting a correctness hole as cosmetic; cost of checking was one 20-minute run of a tool that already existed.

- **llama-bench reads a comma as "run this again", so `-ts 30,3,3,7` is four runs and not one split**: tensor-split is **slash**-separated (`-ts ts0/ts1/..`); the comma is the tool's generic "multiple values for this parameter" separator, documented once at the bottom of `--help` and easy to carry over from every other CLI. Nothing errors — it silently ran four *single-device* configurations, each putting every layer on `Vulkan0`, and surfaced as `failed to allocate Vulkan0 buffer` on a configuration deliberately designed to leave that device nearly empty. **The tell is an OOM naming the device you meant to leave empty**: that is an argument-parsing failure, not a capacity one. Worth knowing at the same time, because it is what sends you to `-ts` in the first place: **`--n-cpu-moe` interacts badly with multi-GPU layer splitting.** llama.cpp splits *layers* evenly across devices, but `-ncmoe` makes per-layer size wildly uneven (3.46 GiB carrying its experts, 0.27 GiB without), so the expert-carrying tail layers pile onto the highest-numbered device — at `-ncmoe 36` all seven landed on `Vulkan3` (26.0 GiB) with `Vulkan0-2` holding 2.98 GiB each, and `-ncmoe 30/24/20/12` all aborted during load with ~90 GiB of VRAM sitting free. An explicit `-ts` moving the device boundaries is the fix.
