# The fp8 GEMV for 2-8 inputs (README step 75, tried, not kept; step 65 measured R and 8/16-wave shared memory before, fp8-multi.txt)
# measured on c4bd99b with temporary changes to hip/fp8_gemv.hip (reverted); bin-hip/bench-fp8 dense-fp8.gguf --ms ..., layer 2, die 0; sclk 6; 2026-11-03
# every variant bit-identical to the one-input call (bench-fp8 --bitwise: 63 of 63 tensor x M cases for 1-3, 27 of 27 for 4)

Why: a 6-token code verify step spends ~0.30 ms per layer in attn.out (wo_a + wo_b), 12.1 ms of the
step on die 0 before the CPU's experts start. At M = 6 the kernel reads weights at ~270 GB/s
(31% of 880) against ~580 at M = 1. Tensors with K >= 4096 (q_a, kv, wo_a, wo_b, the shared
gate/up, engram) split each row over 64 lanes and use the plain kernel: every wave decodes all M
inputs for its 2 rows.

Variants (us per call):
  now       the kernel as it is
  1 fp16    the quantizer also writes the inputs decoded to fp16; the kernel loads them (no decode)
  2 lds     the shared-memory kernel (inputs decoded once per block of 4 waves) for 64-lane rows too
  3 stream  the R weight rows decoded first, then one input at a time (125 -> 67 VGPRs at M = 6,

  4 bounds  3 with the loads issued first and __launch_bounds__(256, 3): 84 VGPRs, 23-29 spilled

Results: none is faster where it matters (M = 4-6 on wo_a/wo_b).
- 1: slower (wo_b M = 6 155 -> 194): decoding is not what limits it; reading the inputs as fp16
  doubles their bytes, and every wave reads all M inputs for only 2 rows.
- 2: faster at M = 3-4 (wo_a 118 -> 95, wo_b 152 -> 134 at M = 4), slower at 6-8: the block decodes
  K x M codes for 8 rows, and the step-39 sweep's verdict holds for the sizes a code step uses.
- 3: higher occupancy yet slower (wo_b M = 6 156 -> 353): each input's load is now waited for just
  before its use, M times a step; the old order keeps all loads in flight.
- 4: the compiler moves the decode back up front, and capping registers spills.
Where it stands: at M = 6 a lane's step is ~270 instructions per 32 weight bytes (8 decodes of 16
codes, 96 dot2, the scales), so the kernel is bound by issue and latency at ~2 waves per SIMD; a
real gain needs a different work split (more rows per wave without holding M decoded inputs, e.g.
inputs in shared memory with 8+ waves per block), which changes the kernel's structure, not one loop.
Not pursued further now (simpler options first: the CPU's verify-step schedule).
